\chapter{Análisis del problema, requisitos, planificación y presupuesto}
\label{chap:metodologia-plan}

\lettrine{E}{n} este capítulo se analiza el problema que aborda el TFG, se fijan los requisitos del sistema y se recoge la planificación de trabajo seguida durante el desarrollo. También se incluyen los riesgos principales, los medios necesarios y una primera estimación económica del proyecto.

\section{Análisis del problema}

El objetivo del trabajo no es construir una instrumentación oceanográfica profesional desde la primera iteración, sino definir un sistema capaz de capturar, gestionar y explotar datos inerciales con una base operativa común para distintas plataformas de adquisición.

La formulación inicial del problema estuvo ligada a la posibilidad de reconstruir directamente la forma de cada ola a partir de medidas inerciales. Tras revisar las limitaciones reales de sensores de consumo y el tipo de información que se maneja habitualmente en este dominio, el problema se reformuló en términos más realistas: obtener parámetros útiles del estado del mar a partir de sesiones inerciales y permitir que esos datos puedan capturarse, almacenarse, consultarse y reprocesarse de forma homogénea.

Esta reformulación tiene dos consecuencias directas. La primera es que la captura deja de estar asociada a una única plataforma. La segunda es que el valor principal del sistema pasa a estar en la organización del flujo completo: adquisición, control, persistencia, comparación y explotación posterior.

Dentro de ese marco, el smartphone se adopta como punto de partida por motivos prácticos: integra sensores, capacidad de procesamiento, conectividad y una interfaz de operación completa. Sobre esa base se plantea la incorporación de un nodo embebido dedicado para comparar plataformas, ganar control técnico sobre la captura y preparar la evolución hacia escenarios de operación remota y multi-nodo.

\section{Requisitos del sistema}

\subsection{Requisitos funcionales}

Los requisitos funcionales principales del sistema son los siguientes:

\begin{itemize}
  \item capturar datos inerciales desde nodos de adquisición heterogéneos, incluyendo nodo móvil Android y nodo embebido ESP32+IMU;
  \item almacenar sesiones con metadatos trazables;
  \item visualizar estado de nodo, sesiones y resultados de forma operativa;
  \item exportar sesiones para análisis externo;
  \item soportar comandos básicos de control remoto, como inicio, parada, estado y configuración;
  \item permitir que la lógica de captura permanezca desacoplada de la interfaz, de modo que la operación pueda realizarse con la app en segundo plano o como consola de supervisión.
\end{itemize}

\subsection{Requisitos no funcionales}

Además de la funcionalidad visible, el sistema debe cumplir los siguientes requisitos no funcionales:

\begin{itemize}
  \item modularidad entre adquisición, comunicación, backend y visualización;
  \item mantenibilidad para evolucionar backend o transporte sin rehacer el sistema;
  \item bajo coste de despliegue en entorno de TFG;
  \item trazabilidad de sesiones y de parámetros de ejecución;
  \item facilidad de operación en laboratorio y escenarios remotos;
  \item capacidad de escalar a escenarios con más de un nodo sin degradación operativa inaceptable.
\end{itemize}

\subsection{Restricciones técnicas}

Las restricciones técnicas más relevantes son:

\begin{itemize}
  \item heterogeneidad de sensores y temporización en Android;
  \item limitaciones de recursos y estabilidad de integración en ESP32;
  \item necesidad de definir contratos de datos comunes entre nodos;
  \item tiempo de desarrollo limitado para cerrar integración extremo a extremo;
  \item incertidumbre sobre qué transporte remoto aporta mejor equilibrio en este alcance;
  \item necesidad de estimar experimentalmente la capacidad práctica del sistema en escenarios multi-nodo, en función de frecuencia de envío, tamaño de mensaje y latencia aceptable.
\end{itemize}

\section{Casos de uso principales}

Los casos de uso que estructuran el sistema son:

\begin{itemize}
  \item configuración remota y consulta de estado de nodos de captura;
  \item inicio y parada remotos de adquisición sobre nodos móviles o embebidos;
  \item recuperación, consulta histórica y reprocesado de sesiones capturadas;
  \item comparación de sesiones entre nodos o dispositivos bajo un mismo flujo de explotación;
  \item supervisión de operación con la app actuando como interfaz de control, sin depender de interacción continua en primer plano.
\end{itemize}

\section{Metodología y planificación}

\subsection{Enfoque de trabajo}

Se adopta una \textbf{metodología incremental} con un \textbf{diseño modular}. El trabajo parte de un análisis inicial del problema, del estado del arte y de las tecnologías disponibles para definir la solución. A partir de ahí, el desarrollo se organiza en iteraciones sucesivas en las que se implementa y valida un bloque funcional del sistema.

Este enfoque permite cerrar primero una base operativa del producto y reducir bloqueos por dependencias de infraestructura, integración o hardware. Además, facilita revisar decisiones con entregables intermedios y ajustar el alcance con el tutor conforme avanza el proyecto.

Durante el desarrollo se plantean reuniones periódicas con el tutor para revisar el avance, evaluar las decisiones tomadas y ajustar el trabajo en función de las indicaciones recibidas.

De forma resumida, la estrategia por bloques funcionales es:

\begin{enumerate}
  \item captura y persistencia de sesión en local;
  \item interfaz operativa Android y gestión de sesiones;
  \item integración local con ESP32 vía interfaz de red;
  \item incorporación progresiva de supervisión y acceso externo a datos;
  \item evaluación final del sistema y propuestas de mejora.
\end{enumerate}

\subsection{Fases del proyecto}

La planificación general del trabajo se descompone en las siguientes fases:

\begin{itemize}
  \item \textbf{Fase 1.} Análisis de trabajos relacionados en sensores inerciales, análisis de movimiento y arquitecturas de captura de datos.
  \item \textbf{Fase 2.} Estudio de limitaciones y características de sensores IMU y técnicas de análisis aplicables.
  \item \textbf{Fase 3.} Definición de la solución y de la interacción entre sus módulos.
  \item \textbf{Fase 4.} Implementación de captura y gestión de datos en diferentes plataformas.
  \item \textbf{Fase 5.} Evaluación del sistema desarrollado y análisis de comportamiento, limitaciones y mejoras.
  \item \textbf{Fase 6.} Aplicación del sistema al caso práctico propuesto.
  \item \textbf{Fase 7.} Documentación final y presentación.
\end{itemize}

\section{Riesgos y estrategia de validación}

Como todo proyecto de desarrollo, el trabajo presenta riesgos técnicos que conviene identificar desde el principio para evitar bloqueos significativos. Los más relevantes son:

\begin{itemize}
  \item \textbf{Desalineación entre nodos:} fijar un contrato de sesión común y validarlo en ambos modos de captura.
  \item \textbf{Inestabilidad de integración embebida:} mantener diagnósticos de conexión, bus y captura.
  \item \textbf{Acoplamiento excesivo a backend o transporte:} mantener desacopladas las capas de comunicación y persistencia.
  \item \textbf{Sobrecarga de alcance:} priorizar una base operativa funcional antes de añadir extensiones opcionales.
\end{itemize}

Desde el punto de vista de validación, el trabajo requiere comprobar no solo la captura aislada en cada plataforma, sino también la consistencia del flujo completo entre adquisición, sesión, consulta y explotación. En esta misma línea, la evolución hacia escenarios con más de un nodo hace recomendable medir de forma experimental la capacidad práctica de comunicación bajo diferentes tasas de envío y tamaños de mensaje.

\section{Material y medios necesarios}

Los medios necesarios para ejecutar el proyecto son:

\begin{itemize}
  \item PC para desarrollo, pruebas y análisis de resultados;
  \item dispositivo móvil Android con sensores inerciales;
  \item plataforma embebida para captura de datos con conectividad inalámbrica;
  \item sensor IMU externo, con acelerómetro y giróscopo;
  \item herramientas de desarrollo software y entornos de programación;
  \item herramientas para almacenamiento, visualización y análisis de datos.
\end{itemize}

\section{Presupuesto orientativo}

Con el objetivo de reflejar de forma más realista el esfuerzo material del proyecto, se distinguen dos lecturas del presupuesto:

\begin{itemize}
  \item \textbf{recursos utilizados por el proyecto}, incluyendo medios ya disponibles pero necesarios para desarrollar y validar el sistema;
  \item \textbf{adquisiciones imputables al proyecto}, centradas en el material específico comprado para la implementación.
\end{itemize}

Los valores de esta primera versión deben entenderse como una referencia preliminar pendiente de ajuste final con datos verificados.
