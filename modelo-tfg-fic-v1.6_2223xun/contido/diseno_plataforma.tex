\chapter{Diseño de la plataforma}
\label{chap:diseno-plataforma}

\lettrine{E}{l} diseño se centra en una arquitectura modular, con Android como interfaz principal y capacidad de integración con un nodo embebido basado en ESP32+IMU.

\section{Enfoque metodológico de diseño}

El sistema se diseña como un sistema ciberfísico por capas.
Este enfoque permite separar responsabilidades y evolucionar componentes sin rehacer el producto completo.

Desde esta perspectiva, la plataforma se organiza en cuatro capas:

\begin{itemize}
  \item \textbf{adquisición}: captura de datos inerciales en nodos móvil y embebido;
  \item \textbf{comunicación}: transporte de comandos, estado y sesiones;
  \item \textbf{backend}: persistencia y sincronización de información;
  \item \textbf{interfaz/control}: operación del sistema y explotación de resultados.
\end{itemize}

\section{Arquitectura funcional}

La arquitectura global contempla dos modos operativos:

\begin{itemize}
  \item \textbf{Modo móvil}: Android captura, almacena y explota sesiones de forma autónoma.
  \item \textbf{Modo embebido}: ESP32 adquiere y Android supervisa, descarga y gestiona sesiones.
\end{itemize}

\subsection{Arquitectura física}

El despliegue físico básico se compone de teléfono Android, nodo ESP32 y IMU externa.
Según el escenario, la adquisición puede realizarse íntegramente en el teléfono o delegarse en el subsistema embebido.

\subsection{Arquitectura lógica y software}

A nivel lógico, el sistema se divide en módulos desacoplados:

\begin{itemize}
  \item captura y normalización de muestras;
  \item persistencia y catálogo de sesiones;
  \item comunicación entre nodos;
  \item visualización, operación y exportación.
\end{itemize}

Esta separación facilita mantenimiento, pruebas y evolución de backend/transporte.

\section{Diseño de contratos de interfaz}

\subsection{Contrato de sesión}

La sesión es la unidad principal de intercambio entre subsistemas.
El contrato de sesión incluye, como mínimo:

\begin{itemize}
  \item \texttt{device\_id};
  \item \texttt{source} (móvil/embebido/simulado);
  \item \texttt{timestamps};
  \item \texttt{fs} estimada;
  \item \texttt{payload} de muestras inerciales;
  \item metadatos de calidad y contexto.
\end{itemize}

\subsection{Contrato de control}

Para operación remota y coordinación de nodos se define un contrato mínimo de control:

\begin{itemize}
  \item \texttt{start};
  \item \texttt{stop};
  \item \texttt{set\_config};
  \item \texttt{status}.
\end{itemize}

\subsection{Contrato de explotación}

La capa de explotación proporciona operaciones homogéneas de:

\begin{itemize}
  \item listado de sesiones;
  \item detalle de sesión;
  \item exportación de datos.
\end{itemize}

\section{Diseño del subsistema de adquisición}

La adquisición se mantiene desacoplada del resto de capas para permitir cambios de nodo sin romper el flujo global.

\subsection{Adquisición en modo móvil}

Android registra sensores inerciales, crea sesiones locales y permite revisión inmediata de resultados.
Este modo sirve como camino base del sistema por simplicidad operativa.

\subsection{Adquisición en modo embebido}

En modo embebido, ESP32 se encarga de la captura y Android actúa como consola de operación y descarga.
La comunicación entre ambos se basa en un conjunto acotado de endpoints y estados de captura.

\subsection{Almacenamiento de sesiones}

El almacenamiento se diseña para trazabilidad y reutilización:

\begin{itemize}
  \item persistencia local durante captura;
  \item metadatos de origen y configuración;
  \item compatibilidad con sincronización a backend.
\end{itemize}

\section{Diseño del subsistema de comunicación}

La capa de comunicación se diseña para soportar dos escenarios:

\begin{itemize}
  \item \textbf{enlace local} Android-ESP32 para operación de laboratorio y pruebas de integración;
  \item \textbf{sincronización remota} con backend para consulta y operación desacoplada.
\end{itemize}

El objetivo es evitar dependencia fuerte de un único transporte.

\section{Diseño del backend}

\subsection{Criterios de diseño de backend}

El backend se diseña como capa intercambiable, con independencia de proveedor o tecnología concreta.
En esta capa se contemplan las siguientes capacidades mínimas:

\begin{itemize}
  \item persistencia de metadatos de sesión;
  \item almacenamiento de ficheros o exportaciones;
  \item sincronización de estado entre nodos.
\end{itemize}

\subsection{Estrategia de evolución tecnológica}

La selección tecnológica final del backend y del transporte de comunicaciones se plantea por criterios de validación práctica:
latencia operativa, robustez de despliegue, mantenibilidad y coste.
Este enfoque evita cerrar prematuramente la arquitectura a una única solución.

\section{Flujo de datos extremo a extremo}

El flujo completo del sistema se define así:

\begin{enumerate}
  \item adquisición de muestras;
  \item normalización y empaquetado de sesión;
  \item persistencia local y/o sincronización remota;
  \item recuperación para visualización, comparación y exportación.
\end{enumerate}

\section{Diseño del subsistema de procesado}

El procesado se mantiene como bloque desacoplado de la captura.
Esto permite reemplazar o evolucionar métodos de análisis sin alterar los contratos de adquisición y comunicación.

La arquitectura exige que cualquier bloque de procesado cumpla:

\begin{itemize}
  \item entrada basada en contrato de sesión;
  \item salida estructurada y trazable;
  \item compatibilidad con ambos orígenes (móvil y embebido).
\end{itemize}

\section{Diseño hardware del sistema embebido}

El subsistema embebido se compone de ESP32, IMU y electrónica auxiliar de conexión/alimentación.
Su papel en la arquitectura es doble: adquisición dedicada y validación de interoperabilidad con la app Android.
